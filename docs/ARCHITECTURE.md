# 多人模式架构方案

> **结论：技术栈不换，运行模型必须换。**
>
> 不换 Three.js / 原生 ES Module / 静态托管 —— 它给你的东西（1.7MB 全站、秒开、手机浏览器直开）恰恰是 3D 页游的命门。
> 必须换的是**代码怎么组织、游戏在哪台机器上跑**：现在是一个 `Game` 对象同时管渲染、输入、模拟、UI、上传，这套结构只能跑单机，加多少功能都变不成多人。
>
> 时机是**现在**。因为多人是既定目标，而改造成本随功能数量超线性增长：现在改 1-2 周，加完皮肤/赛季再改 1-2 个月，等 8 人房间上线后再改基本等于重写。

---

## 一、先回答"换不换引擎"

我把可选项的代价摊开算了，结论没有悬念：

| 方案 | 首包体积 | 移动端表现 | 现成网络方案 | 重写成本 | 判断 |
|---|---|---|---|---|---|
| **Three.js（现在）** | 全站 1.7MB，gzip 后约 500KB | 好，浏览器直开 | 无，需自研 | 0 | **保留** |
| Unity WebGL | 空项目 8-15MB，实装 25MB+ | iOS Safari 内存吃紧、微信 X5 内核 WebGL2 不稳 | NGO / Mirror / Photon，很强 | 3-6 个月 | 否 |
| Godot 4 Web | 10-20MB | 需 COOP/COEP 头才能多线程 | 生态薄 | 3-5 个月 | 否 |
| Cocos Creator 3D | 5-10MB | 国内生态好 | 第三方，一般 | 2-3 个月 | 否 |
| Babylon.js | 接近 Three | 好 | 无 | 1-2 个月 | 无收益 |

**换引擎唯一能买到的是"现成的网络同步库"**（Photon Fusion 的预测回滚确实是工业级）。但代价是：包体涨 10-20 倍、首屏从 1 秒变 8 秒、iOS 微信里随时崩、5 千行已经调好手感的代码全部作废。

而多人坦克游戏恰恰是**最不需要高级网络库**的那一类：车慢、弹道可预测、对 50-80ms 延迟不敏感。20-30Hz 权威服务器 + 客户端预测，手写 2000 行足够，而且完全可控。

> 一句话：**你缺的不是引擎，是"游戏跑在哪"这个决定。**

---

## 二、3dtank 这类游戏到底是怎么跑的

参考对象没错，但它值得抄的不是画面，是**部署模型**：

1. **房间制，不是开放世界。** 大厅 → 建房/进房 → 一局 5-15 分钟 → 结算回大厅。房间是天然的隔离单位和扩容单位：一台机器挂几百个房间，加机器就是加房间数。你现在的"一局到底、死了重开"其实已经是房间的雏形，只差把它搬到服务器上。
2. **权威服务器 + 客户端预测。** 服务器算一切，客户端只发"我要往前开、我要开炮"。玩家自己的坦克本地立刻响应（预测），别人的坦克插值显示。这类游戏从不做帧同步、也不做回滚。
3. **内容全是数据表。** 车体、炮塔、炮弹、皮肤都是配置，不是 `if (id === 'heavy')` 这种分支。所以它每个赛季能上新内容而不用动网络层 —— 这正是你要的"稳定运行和升级"。

它有三件事你**不要**抄：端游级的美术管线、多区域机房、自研引擎。那是一个团队十年堆出来的，不是一个人该碰的。

## 三、现在这套代码，具体哪里挡路

不是"代码烂"，是五个假设和多人直接冲突。每一条都能在代码里指到行：

| # | 现状 | 位置 | 为什么多人做不了 |
|---|---|---|---|
| 1 | 模拟与渲染写在同一个方法里 | `Game.update()`，1458 行的类 | 服务器上没有 DOM 和 renderer，这段代码搬不走 |
| 2 | 实体创建即建模型 | `new Tank(scene)` / `new Enemy(scene)` | Node 里跑模拟需要先有 canvas |
| 3 | 可变步长 | `Math.min(clock.getDelta(), 0.05)` | 同输入不同结果，服务端算的不能是"唯一真相" |
| 4 | 全局随机流 | `Math.random = mulberry32(...)` | 玩家开火会推进刷怪序列；多房间互相踩踏；**所谓"同一天的每日挑战"其实每个人打的不是同一局** |
| 5 | 成绩由客户端上报 | `_submitRun` | 改一行 JS 就能刷分。多人/赛季/会员全部无解 |

第 4 条是我上一轮已经动手改掉的部分（拆成 `spawn / combat / fx` 三条独立流），第 5 条只做了一半（榜单加了挑战码与车型字段）。**这两块是纯收益，与架构选型不冲突，可以先留着**；其余三条要等架构定了再动。

## 四、目标架构：三层，一个核

不搞 monorepo，不引打包器。就用目录分权，Node 直接 import 浏览器同一份 `.js` —— 少一层构建，就少一类"本地能跑线上炸"的问题。

```
roguetank/
├── src/
│   ├── shared/              ← 唯一真相层，禁止 import three、禁止碰 document
│   │   ├── sim/
│   │   │   ├── World.js     实体表、固定步长 step()、快照 snapshot()
│   │   │   ├── entities/    PlayerTank / EnemyTank / Projectile（纯数据）
│   │   │   └── systems/     movement / weapon / spawn / collision / nav
│   │   ├── data/            weapons.js chassis.js upgrades.js modifiers.js（纯配置）
│   │   └── net/             protocol.js（消息 schema）codec.js（增量编解码）
│   ├── client/              ← 只负责"把服务器说的画出来"
│   │   ├── render/          TankView / EnemyView / Effects / Minimap
│   │   ├── input/           键鼠 → 命令帧
│   │   ├── ui/              HUD / 大厅 / 房间 / 结算
│   │   └── transport/       LocalTransport（Worker）· WsTransport
│   └── server/              ← 只负责"房间里发生什么"
│       ├── Room.js          房间生命周期、tick 循环
│       ├── Lobby.js         房间列表、建房、房间码
│       └── auth.js          身份、成绩落库
├── server.mjs               ← 本地静态服务（开发）
├── node-server.mjs          ← 联机服务器入口（生产）
└── functions/api/           ← 榜单等轻接口（可保留在 Pages）
```

运行时两条链路，**同一份 sim**：

```
单机：  client/input ─→ LocalTransport(Web Worker 里的 Room) ─→ client/render
联机：  client/input ─→ WebSocket ─→ server/Room(权威) ─→ WebSocket ─→ client/render
```

**最关键的一条设计：单机也走 `Transport`，也要过一遍房间。** 单机时房间跑在 Web Worker 里，延迟 0，但代码路径和联机完全一致。

这一条决定了你不会"做到一半再换"——因为你每天都在跑联机的那条链路，只是传输层换了个实现。等真要上线多人时，改的是一个 `new WsTransport()`。

## 五、五个现在必须定死的决策

这几件事一旦写进代码就改不动了，现在定，比以后改便宜一百倍。

**1. 时间是 tick，不是秒。**
服务器 30Hz 固定步长（`dt = 1/30`），客户端渲染 60fps 做插值。所有冷却、持续时间、波次计时都按 tick 计数。现在的 `dt` 到处传，改成 tick 会让代码更简单，而不是更复杂。

**2. 客户端只发"意图"，永远不发"结果"。**
```js
Command = { seq, tick, throttle, steer, turretYaw, fire, ability }
```
服务端收到后自己算移动和弹道。客户端上报坐标 = 把作弊接口直接开在公网上。

**3. 快照分两种：增量 + 关键帧。**
每 2 秒一个全量关键帧（用于中途加入、丢包恢复），其余发增量。字段做量化：坐标 int16（1cm 精度）、朝向 int8（1.4° 精度）。一辆坦克约 9 字节。

**4. 炮塔朝向必须独立同步。**
你的坦克是车体 + 炮塔分离的（`Tank.js` 里 `turret` 有独立 yaw）。同步时如果只发车体朝向，别人的炮塔看起来永远对着车头。这是坦克游戏最容易漏的一处。

**5. 协议带版本号，握手时校验。**
`PROTOCOL_VERSION = 1`。版本不匹配就提示刷新，而不是让老客户端连上来制造一堆灵异 bug。上线后每次改协议 +1。

## 六、合作模式具体怎么同步

**权威归属**：服务端。不是房主权威。房主权威会遇到掉线全房崩、房主改包、NAT 穿透三个死结，省下的服务器钱不值。

| 对象 | 客户端处理 | 说明 |
|---|---|---|
| 自己的坦克 | 预测 + 校正 | 本地立刻动，收到快照比对，偏差 <3m 软插值拉回，>3m 硬校正 |
| 队友坦克 | 纯插值（100ms 缓冲） | 不预测，看到的是 100ms 前的他，换来丝滑 |
| 敌人 | 纯插值 | 同上 |
| 子弹 | **不发子弹实体，只发"开火事件"** | 客户端各自按弹道参数模拟飞行；命中由服务端判定并下发结果。省 40% 带宽，还不会被"幽灵子弹"恶心到 |

最后一条是带宽的关键。8 人房里 4 个玩家 + 45 个敌人 + 40 发子弹，如果子弹也同步，每帧多 40 个实体；改成事件后实体数从 ~90 降到 ~50。

**玩法层的同步设计（合作 PvE）**：
- 波次是**房间级共享状态**，不是每人一份。
- 敌人血量按 `sqrt(人数)` 放大、数量按 `n^0.85` 放大 —— 线性放大会变成推墙，不放大会变成切菜。
- **倒地救援**：血量归零 → 倒地 30 秒 → 队友靠近 3 秒拉起。比"死了观战"黏性高得多，也是合作游戏的核心互动。
- **强化各选各的**：每人独立三选一，不共享卡池。一个人玩奶妈流、一个人玩爆发流，才有分工可言。
- 中途加入：发一个关键帧就能重建世界，不需要"等这波打完"。
- 断线重连：保留席位 60 秒。

## 七、部署与成本：算给你看

先算带宽（这是真正的瓶颈，不是 CPU）：

- 4 人房，约 50 个同步实体，20Hz 快照，每实体 9 字节增量 ≈ 每帧 450B + 帧头
- 每人下行 ≈ **12 KB/s（约 96kbps）**，4 人房 ≈ 48 KB/s
- 5Mbps 轻量服务器（≈ 625 KB/s）→ **约 12 个满房**
- 100Mbps → 200+ 房

CPU 反而不值一提：30Hz × 50 实体 ≈ 1500 次更新/秒/房，Node 单核跑 100 房没问题。

| 方案 | 延迟（国内） | 月成本 | 适用 |
|---|---|---|---|
| **国内轻量云 2C4G**（阿里/腾讯） | 20-50ms | ¥60-100 | **正式上线选它**，一台先扛首批用户 |
| Cloudflare Durable Objects | 150-300ms，抖动大 | 免费额度够 | 海外用户 / 快速验证，一个房间一个 DO，运维为零 |
| 自建海外 VPS | 200ms+ | $5-20 | 不推荐给国内玩家 |

架构上只要 `shared/sim` 不依赖 Node 专有 API（`fs`/`net`），DO 和普通 VPS 都能跑，随时能搬。**这是"不锁死"的唯一保证**：部署商可以换，代码不用换。

## 八、迁移路线：四个阶段，单机全程可玩

每一步都能独立上线、独立回退。没有"大爆炸式重写"。

**P0 · 抽核（1 周）**
把 `Game.js` 里的模拟段搬进 `shared/sim`，实体拆成"状态 + 视图"。渲染层改成读快照画图。
同时交付一个无头脚本：`node test/sim.mjs --seed 12345 --input script.json` 能跑完整局并输出战报。
*验收：单机手感不变，Node 里能跑完一整局。*

**P1 · 单机走完整链路（1-2 周）**
房间跑进 Web Worker，客户端只通过 `LocalTransport` 和房间说话，不再直接碰 sim。
渲染改成插值（即使 0 延迟）。
*验收：把 `LocalTransport` 换成 `WsTransport`，游戏应该能直接跑，不需要改别的。这一步做对了，后面全是配置。*

**P2 · 真联机（2 周）**
`node-server.mjs` + `ws`，房间码 6 位，2-4 人合作 PvE，倒地救援，断线重连。
*验收：两台设备同房，150ms 延迟下手感可接受，中途加入不闪退。*

**P3 · 规模化（持续）**
8v8 PvP、匹配、账号、赛季、观战、回放。

**为什么这个顺序不会再返工**：P1 结束时，单机和联机共用一条链路。之后加任何玩法（新武器、新敌人、新模式），改的都是 `shared/sim` + `shared/data`，两个宿主自动同步。**这就是"不会做到一半再换架构"的技术定义。**

## 九、三条验收判据（用来证明架构真的对了）

不是靠感觉，靠三个可以自动跑的判断：

1. **删掉 `src/client/`，服务器仍能跑完一整局并输出战报。** —— 证明模拟真的独立了。
2. **单机模式下打开 DevTools，看到的是 Worker 消息，而不是直接调用 `world.step()`。** —— 证明链路统一了。
3. **新增一把武器只改 `shared/data/weapons.js`，协议版本号不变。** —— 证明内容与网络解耦了。

任何一条不成立，就说明还没拆干净，别急着往上加功能。

## 十、明确不要做的事

- **不要上微服务、K8s、Redis 集群。** 你是一个人，运维复杂度会直接杀死项目。一个 Node 进程 + 一个 Postgres/SQLite 就是全部。
- **不要做 P2P 房主权威。** 三个死结，省不下钱。
- **不要做帧同步/回滚网络。** 那是格斗游戏的需求，坦克用不上，只会把工期拖成三倍。
- **不要先做 PvP。** PvE 合作对同步精度的要求低一个数量级，先用它把链路跑通。
- **不要在客户端做任何权限判断。** 客户端里的 `if (isMember)` 只是 UI，真正的门永远在服务端。
- **不要为了联机砍掉单机。** 单机是漏斗顶端，点开就能玩，是拉朋友进来的入口。

## 十一、会员的位置（一句话）

会员建在账号上，账号建在服务端权威上。**先把 P2 跑通，账号和权益是水到渠成的事**；反过来先做会员，等于把收银台盖在流沙上。权益卖外观、便利、房间容量，不卖数值——肉鸽的乐趣一旦能用钱买，排行榜就失去意义。

## 附录 B：开放世界 vs 房间制

### 这不是"更大的房间"，是另一个问题

| | 房间制 | 开放世界 |
|---|---|---|
| 世界生命周期 | 一局 5-15 分钟，结束即销毁 | 持久运行，数月不重启 |
| 状态存哪 | 内存，随房间释放 | 必须落库：位置、装备、进度、载具 |
| 扩容单位 | 房间（加机器 = 加房） | 世界分线（同一张图开 N 条） |
| 单实例上限 | 8-16 人 | 60-100 人（受 CPU 与带宽硬顶） |
| 崩了会怎样 | 一个房间的人掉线 | **整条线回档，玩家进度丢失** |
| 热更新 | 直接换新房间 | 世界不能停，必须支持不停服更新 |

### 人数上限：设数字容易，难的是"满了之后"

`capacity` 就是一个配置字段，两种模型都能设。真正的分水岭是：

- **房间满了** → 再开一间。成本线性增长，永远有位置。**这是唯一"无痛"的扩容方式。**
- **开放世界满了** → 只能分线。分线意味着同一张地图有 1 线、2 线、3 线，朋友很容易进不到同一条线；还要处理跨线迁移、跨线交易、跨线排行榜。这是所有 MMO 都绕不开的复杂度。

### 带宽实测估算（按 20Hz、每实体 9 字节量化）

| 模型 | 单实例人数 | 单实例出口带宽 | 5Mbps 机器能开几个 |
|---|---|---|---|
| 4 人合作房 | 4 + 50 AI | ~36 KB/s | 约 17 房（68 人） |
| 8v8 房 | 16 + 少量 AI | ~150 KB/s | 约 4 房（64 人） |
| 社交 Hub（只同步移动） | 30-50 | ~90-150 KB/s | 约 5 线（200 人） |
| 开放世界单线 | 60-100 + 500 AI | ~900 KB/s | **1 条都跑不满** |

最后一行的意思是：开放世界单条线就需要 10Mbps 以上，而且 CPU 会被 500 个 AI 的寻路吃光。房间制在同样的钱下能装的人**多 3-5 倍**。

### 对肉鸽游戏，开放世界有一个设计层面的冲突

你的核心循环是"局"：随机词条 → 一次性 build → 死亡结算 → 排名。排行榜、每日挑战、挑战码，全都建立在"局"这个概念上。

开放世界会消解"局"：没有波次、没有结算、死亡没有代价、build 可以无限累积。这不是技术选择，是**把肉鸽改成了 MMO**，上面的三样东西同时失效。

### 推荐：Hub + 副本（半开放）

业界成熟做法，也是最适合你的：

- **一个持久的社交 Hub**（30-50 人）：看别人改装、看排行榜墙、组队、试车场。只同步位置/朝向/外观，不算战斗，负载比房间低一个数量级，代码可以复用客户端渲染层。
- **战斗仍然是 4 人实例**：点 Hub 里的"出击门"进副本，打完回 Hub。

好处是"一起玩"的社交感有了，但每局仍然完整、可排名、可分享。技术上只是把房间制包了一层大厅，**不需要 AOI、不需要世界持久化、不需要热更**——这三样才是开放世界真正的成本（6-12 个月）。

### 如果坚持要做开放世界，架构要加的六样东西

1. **AOI 兴趣管理**（九宫格 / 四叉树）：只同步玩家周围的实体，否则 100 人互相全量广播直接爆带宽。
2. **世界持久化**：玩家位置、载具、背包、进度实时落库，且要能崩溃恢复。
3. **世界分区与跨区迁移**：地图切成 cell，玩家跨 cell 时要无缝交接。
4. **不停服热更新**：世界不能停，新代码要能在线加载。
5. **GM 工具与回档机制**：开放世界出事故是常态，必须有回滚能力。
6. **单点故障预案**：一个世界进程 = 一个单点，必须热备。

这六样没有一样能"顺手做掉"，每一样都是独立工程。
