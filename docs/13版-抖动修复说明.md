# 13 版 · 抖动根因修复说明

> 这一版不再"打补丁"，而是回到 08 版第一版，用可复现的仿真实测出抖动的**真实来源**，再逐个改掉。

---

## 一、结论先说

抖动的**真因**不是网络、不是服务器性能、也不是"校正太激进"，而是两个**代码级的设计缺陷**，都存在于 08 版第一版里，之前 4 个版本（08~12）的补丁都没有触到它们：

| # | 缺陷 | 位置 | 症状 |
|---|---|---|---|
| 1 | 渲染外推方向用了**车头朝向**，而不是实际位移方向 | `coop.js` `_reconcile` | 一开动就抖；高刷屏上更明显 |
| 2 | 预测偏差的"保险丝"让偏差**永远收敛不回来** | `coop.js` `_absorbResidual` | 车会自己飘/自己抖，偏差可达 20 米以上 |

另外顺手修掉了 3 个此前报告过的问题（房间 60~77 秒消失、房间码字母替换、快照节奏锯齿）。

---

## 二、缺陷 1：外推方向错了

### 现象

车头不是瞬间转向的——它按 8 rad/s 追移动方向，往左横移要 **11 个 tick（0.37 秒）** 才转齐。但位移是**立即**生效的。

旧代码这样算渲染位置：

```js
const vx = Math.sin(this.me.yaw) * this.me.speed;
const vz = Math.cos(this.me.yaw) * this.me.speed;
let rx = this.me.x + vx * acc;
let rz = this.me.z + vz * acc;
```

`acc` 是"本 tick 已过去的时间"，每个 tick 都归零重来。所以车头没转齐的这 0.37 秒里，**每一帧的外推方向都和真实位移不一致，而且每 tick 被重算一次**。

### 实测数据（确定性仿真，60/75/144fps）

| 策略 | 60fps 步长波动 | 75fps | 144fps | 最大帧间方向突变 |
|---|---|---|---|---|
| **旧：yaw 外推** | **197%** | **246%** | **454%** | **90°** |
| 新：实测位移 | 0% | 0% | 0% | 0° |

144fps 下最露骨：**每两帧就有一帧是倒退着画的**（位移为负）。

### 修复

```js
// 量"这一步真正走了多远"，方向/撞墙滑行/地形减速全部自动正确
this._vel.x = (this.me.x - this._predFrom.x) / (ticksThisFrame * TICK_DT);
this._vel.z = (this.me.z - this._predFrom.z) / (ticksThisFrame * TICK_DT);
```

外推时用 `_vel`，不用 `sin(yaw)*speed`。同时：

- **静止时直接贴逻辑位置**，不做任何收敛动画 → 不按方向键时画面一毫米都不动；
- 行驶时用「速度前馈 + 25ms 软约束」，稳态与逻辑位置零误差，且不会冲过头再往回走。

## 三、缺陷 2：偏差永远收不回来

### 现象

`_absorbResidual` 的逻辑是：

- 行驶中只消化**横向**残差，纵向（沿前进方向）"故意不追"；
- 残差记进 `_shift`，上限 1.2 米；
- 3 米以上才"直接归位"。

问题是：只要客户端相对服务端**稳定领先**，每一帧都会往 `_shift` 里塞一点纵向残差 → 撞上 1.2 米保险丝后**停在那儿** → 而 3 米的归位阈值**永远够不到**。

结果：偏差无限期卡在 1.2 米，每帧还在往里塞。**实测（空场、80ms RTT）偏移涨到 24 米以上**，同时表现成"车自己在飘、自己在抖"。

### 修复

先看**绝对**偏差，超过 2.0 米就整段贴回权威位置：

```js
const absErr = Math.hypot(rx, rz);
if (absErr > MAX_PRED_ERROR) {   // 2.0 米
  this.me.x = snapPos.x;
  this.me.z = snapPos.z;
  // 渲染位置一起贴，避免下一帧从 20 米外"飞"回来
  this._disp.x = snapPos.x;
  this._disp.z = snapPos.z;
  ...
  return;
}
```

2.0 米略小于半个车身，肉眼完全看不出，但足以在撞墙分叉、卡顿漏帧、地形边界分歧上立刻归位。同时 `_shift` 的写入从 `+=` 改成 `=`（幂等，同一份快照算多少遍结果一样）。

## 四、顺手修掉的三个老问题

### 4.1 房间 60~77 秒后消失

**根因**：一个人挂机被打死 → `world` 全员阵亡 → `state='over'` → 8 秒后 `destroy()`，房间码从索引消失。创建者的连接还在、还在收快照，但朋友再也进不来。

**修复**：`over` 时先看在线人数。还有人连着 → `world.reviveAll()` 全队复活回出生点 + 直接重开；真没人在线才结算销毁。

### 4.2 `O→0→2`、`I→1→J` 的归一化怪

**根因**：链式替换 `O→0→2`，玩家照着屏幕敲反而进不去；`0` 和 `1` 还会被二次替换成 `2` 和 `J`。

**修复**：`normalizeRoomCode` 只做「去空白 / 转大写 / 掐 4 位」，**不替换任何字符**，合法性交给 `ROOM_CODE_RE` 判定，非法就明确报 `bad-code`。

### 4.3 快照节奏锯齿

**根因**：20Hz 快照配 30tick，`30/20 = 1.5` 不是整数 → tick 差在 1 和 2 之间来回跳（2,1,2,1…）→ 客户端按 tick 插值的段长忽长忽短。

**修复**：`SNAPSHOT_RATE = 15`（`30/15 = 2`，整除），服务端改用 **tick 累加器**判定（满 2 个 tick 发一帧），tick 差恒为 2，不受宿主调用节奏影响。

## 五、追猎者 / 猎豹：改回全向炮塔

| 车体 | 原射界 | 现射界 | hp | speed | turn | 炮塔转速 |
|---|---|---|---|---|---|---|
| 轻装突击型（猎豹） | ±15° | **全向 180°** | 90 | 20 | 3.6 | 170°/s |
| 猎手型（追猎者） | ±15° | **全向 180°** | 110 | 17.5 | 3.2 | 170°/s |

**除射界外，所有数值一个都没动。** 转速仍是 170°/s（不是瞬间对准），所以手感依然是"重炮塔"，只是不再被锁在车头 ±15° 里。

卡面文案同步更新为「全向炮塔」。

## 七、部署

```bash
# 1. 上传并覆盖（保留 .data/ 里的榜单数据）
tar -xzf roguetank-2026-11-08-13.tar.gz -C /path/to/roguetank

# 2. 重启（必须做，覆盖文件不等于生效）
pm2 restart roguetank

# 3. 两端都强刷
#    浏览器里 Ctrl+Shift+R
```

### 部署后自检

打开浏览器控制台执行：

```js
__game.net.netstat
```

应看到 `hz ≈ 15`、`ticks ≈ 2`（tick 差恒为 2）。如果不是，说明服务端没重启成功。

## 八、如果还有抖动

这一版把两个已知根因都消掉了。如果部署后仍有抖动，请帮我确认一个关键区别：

- **只有自己的车在抖，建筑/地面的相对位置是稳的** → 问题在渲染层，请描述是"静止时抖"还是"一开动就抖"
- **整个画面一起抖（建筑也在动）** → 问题在相机层，属于另一套代码

另外请附带 `__game.net.netstat` 的输出（`hz` / `ticks` / `gapMax` / `stalls`），这三个数字能立刻区分"服务端没重启"和"网络抖动"。
