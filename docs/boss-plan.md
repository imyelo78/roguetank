# Boss 扩展方案

> 状态：待评审，**代码未动**。评审通过后再分阶段实施。
> 当前版本 r45（`5c5ac8e`）：已删除棱镜的相位跃迁（方案 C）。

## 一、现状盘点

### 1.1 现有阵容

| Boss | 波次 | 战斗形态 | 单机技能 | 联机技能 |
|---|---|---|---|---|
| 破城者 breaker | 5 / 15 / 25 … | 重甲远程炮台，7.2 m/s，34m 射程 | 主炮单发（提前量 + 俯角解算） | 主炮单发 |
| 棱镜 prism | 10 / 20 / 30 … | 轻型游击炮台，9.2 m/s，40m 射程 | 三连点射 + 折射风暴（12/16 发环射）+ ~~相位跃迁~~ | 三连点射（**无技能**） |

轮换规则写死在 `src/core/world.js` 的 `startWave()`：

```js
const breaker = Math.floor(n / 5) % 2 === 1;
```

即每 5 波一个 Boss，奇偶交替，只有 2 种。第 25 波起就是第 5 波的原样复读，血量只按 `1300 + n * 300` 线性长。

### 1.2 两套 AI，四个地方各存一份 Boss 信息

这是"加 Boss 很贵"的根因：

| 内容 | 单机 | 联机 |
|---|---|---|
| 基础属性（hp/speed/range/fireCd） | `Enemy.js` 内部按 kind 分支 | `core/world.js` `ENEMY_TYPES` |
| 名称 | `Enemy.js` `BOSS_INFO` | `Game.js:793` 写死三元、`coop.js:1656` 再写一遍 |
| 核心配色 | `Enemy.js` `CORE_MATS` | `coop.js` 按 `typeCode` 映射 |
| 技能逻辑 | `Enemy.js` `_updateBoss` | `core/world.js` `_updateEnemies` |

所以现在加一个 Boss，至少要改 5 个文件、6 处分支，而且两边一定会慢慢分叉 —— 联机棱镜至今没有折射风暴就是活例子。

### 1.3 三个已存在的坑（施工前先修）

1. **联机 Boss 条配色失效**
   `coop.js:1657` 传的是 `boss.type`（`'boss_prism'`），单机 `Game.js:1551` 传的是 `bossKind`（`'prism'`）；
   `styles.css` 只写了 `.boss-bar[data-kind="prism"]` → 联机棱镜的血条一直是破城者的橙红配色。

2. **Boss 名字两套**
   单机「棱镜」，联机「棱镜之眼」，HUD 只在 kind 变化时更新名字（`HUD.js:1000`），同 kind 换名不会刷新。

3. **typeCode 靠数组下标**
   `world.js:1276` 用 `Object.keys(ENEMY_TYPES).indexOf(type) + 1` 生成编码，`coop.js:110` 反向查表。
   往中间插一个类型、或两端版本不一致，就会把 Boss 渲染成 gunner（血条、模型、颜色全错，且不报错）。

## 二、重构：让"加 Boss"变成只改一个文件

### R1 单一数据源 `src/core/bosskit.js`

```js
export const BOSS_LIST = ['boss_breaker', 'boss_prism', 'boss_wraith', 'boss_blitz'];

export const BOSS_META = {
  boss_breaker: { name: '破城者', kind: 'breaker', tag: '重装',
                  core: 0xff6a2a, bar: 'breaker', skills: ['mainGun'] },
  boss_prism:   { name: '棱镜',   kind: 'prism',   tag: '折射',
                  core: 0x6fe6ff, bar: 'prism',   skills: ['burst', 'ring'] },
  ...
};

/** 第 n 波出什么 Boss；非 Boss 波返回 null */
export function bossTypeForWave(n) { ... }
```

单机、联机、HUD、CSS 全部从这里取，删掉所有写死的三元与字符串。

### R2 技能写成"纯逻辑 + 副作用事件"

技能不进渲染层，只吃状态、吐事件：

```js
// 返回值是给渲染层的事件列表，联机还要塞进快照
stepSkill(boss, ctx, dt) -> [{ t: 'warnCircle', x, z, r, dur }, { t: 'teleport', x, z }, ...]
```

- 单机：`Enemy.js` 消费事件 → 建预警圈 mesh、播特效
- 联机：`world.js` 消费事件 → 写进快照字段（`bw: [x, z, r, 剩余时间]`），客户端 `coop.js` 照着画

这样技能只在**一个文件**里实现一次，两端行为天然一致，也不会再出现"单人有、联机无"。

### R3 协议

- `typeCode` 改成 `BOSS_META`/`TYPE_CODE` 显式常量表，与数组顺序解耦
- `PROTOCOL_VERSION` 3 → 4，旧客户端直接拒进（比渲染错要好）
- 快照新增 `bw`（Boss 预警圈）字段；静止区域无需插值

**这一阶段玩家看不到任何变化**，但之后每加一个 Boss 的边际成本会从"改 6 处"降到"往表里加一行 + 写一个技能函数"。

## 三、新 Boss 设计

现有两个都是"远程炮台"，差别只在射速和弹道密度 —— 打起来是同一种节奏：绕圈、躲弹、磨血。四种新 Boss 按**逼迫玩家做的动作**来分，而不是按数值分。

### B1 幽影 wraith（← 原方案 A：预警跃迁）

> 定位：位移型，考"你能不能一直盯住它"

- 每 9s（狂暴 6.5s）一次**相位跃迁**：脚下亮起青色圈，**1.2s 收缩**，收满瞬间传送到玩家周围 12~16m 的随机方位
- 落点必在预警圈内可读 —— 玩家看到圈就知道"它要贴过来了"，可以提前转向或拉开
- 落地冲击波：半径 6m、伤害 8，把"贴脸"变成必须处理的事件，而不是白给
- 血量中等，射程短（28m），靠贴近施压

和原来的瞬移差别：**有 1.2s 预告 + 距离从 17~24m 收到 12~16m**（真的会靠近），从"看不懂的跳变"变成"看得懂的压迫"。

### B2 疾风 blitz（← 原方案 B：短距冲刺）

> 定位：节奏型，考"卡输出窗口"

- 每 7s 一次**冲刺**：0.32s 内沿直线位移 8m，带拖尾与音效，路径上留 3 个残影
- 冲刺结束 **1.5s 硬直**（停止移动与开火，核心闪白）——这是玩家的输出窗口
- 冲锋撞击造成 14 点伤害，判定半径 2.6m，能躲（0.32s 位移是可读的）
- 血少速度快，打法从"绕圈磨"变成"等硬直打一波"

### B3 铁壁 bulwark（新增，机制型）

> 定位：考"你会不会绕后"

- 正面装甲减伤 70%，背面/侧面正常
- 每 12s 展开 4 个护盾发生器（独立血条，各 8% 本体血），全部打掉才能破防 6s
- 移动极慢（4.5 m/s），压迫感来自"你不绕后就是打不动"
- 把"正面装甲"这条已有属性（`shield` 敌人有 `frontArmor: 0.45`）真正用起来

### B4 蜂巢 hive（新增，召唤型）

> 定位：考"清场与优先级"

- 本体不移动，固定在场地中央，射程 60m 的慢速炮
- 每 10s 放出 3 只 drone（复用现有 `drone` 模板），场上上限 9 只
- 血厚（1.6 倍），但小怪不清就会淹死 —— 玩家要在"打本体"和"清小怪"之间做取舍
- 天然适合多人房：分工变得有意义（一人压制本体、一人清怪）

### 阵容与波次编排

| 波次 | Boss | 设计意图 |
|---|---|---|
| 5 | 破城者 | 教学：站桩炮台，学会绕圈 |
| 10 | 棱镜 | 进阶：弹幕密度，学会看弹道 |
| 15 | 幽影 | 变化：位移压迫，学会盯目标 |
| 20 | 疾风 | 节奏：冲刺 + 硬直，学会抓窗口 |
| 25 | 铁壁 | 机制：绕后破防，学会找弱点 |
| 30 | 蜂巢 | 压力：召唤清场，学会分配火力 |
| 35+ | 循环 + 强化 | 每轮 +1 层"狂暴"：技能 CD ×0.85、血量 +25%，上限 3 层 |

35 波之后不再加新 Boss，改用**强化层数**拉长生命周期 —— 加 Boss 的边际收益会越来越低，而"同一个 Boss 打得更凶"成本几乎为零。

### 数值基线

- 血量沿用 `(1300 + n * 300) × hpMul`，按体型乘系数：破城者 ×1.0、棱镜 ×0.9、幽影 ×0.85、疾风 ×0.8、铁壁 ×1.2、蜂巢 ×1.6
- 所有技能**必须有可躲窗口**：预警 ≥0.9s，或位移可读（冲刺 0.32s / 8m）
- 单个技能的满伤不超过玩家满血的 25%（当前玩家 100 → 单次 ≤25）

## 四、实施顺序

| 阶段 | 内容 | 玩家可见变化 | 风险 |
|---|---|---|---|
| **P0** | R1 单一数据源 + R2 技能抽纯函数 + R3 协议升版 | 无（纯重构） | 中：改动面大，但有测试兜底 |
| **P1** | 幽影（预警跃迁）+ 疾风（冲刺），双端同时上 | 第 15/20 波变新面孔 | 中：需要新预警圈渲染 |
| **P2** | 铁壁 + 蜂巢，含护盾发生器/召唤逻辑 | 第 25/30 波 | 高：护盾发生器要独立实体与快照支持 |
| **P3** | 35 波后的强化层数 | 后期曲线变陡 | 低 |

P0 是"地基"，P1 是验证地基是否真的省事 —— 如果 P1 做下来还是要改 6 处，说明 R1/R2 抽取失败，应该停下来重做，而不是硬上 P2。

## 五、验收标准

- `bosskit` 单测：波次轮换、落点约束（不出界、不进建筑、离玩家 ≥12m）、技能 CD 与狂暴系数
- 双端一致性：同一串输入喂给单机与联机世界，Boss 位置/技能触发帧差 ≤1 帧
- 可躲性：每个技能在浏览器里实测"站桩必中、匀速横移可躲"，不允许出现"无解技能"
- 回归：`npm test` 全绿；联机端到端（建房 → 打满 20 波 → 三种 Boss 都出现且技能生效）

## 六、需要你拍的板

1. 六个 Boss 是不是太多？可以先做 P1（幽影 + 疾风）验证手感，再决定要不要 P2
2. 铁壁"护盾发生器"要不要上？它是 P2 里唯一需要新增实体的机制，工作量约等于另外三个技能之和
3. 35 波之后是"强化循环"还是"继续加新 Boss"？我倾向前者
4. 联机难度的目标：现在联机缺技能、比单机简单一截，补完技能后要不要顺带调一次血量系数？
